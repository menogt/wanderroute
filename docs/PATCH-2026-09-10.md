## 1. AI generation was silently failing

### Symptom
Every itinerary came back as the offline "practical standard itinerary" with a toast saying enhanced planning was unavailable. The Netlify function log for `generate-itinerary` was empty.

### Root cause
Groq had retired the model `llama-3.3-70b-versatile`. Every request returned HTTP 404 with the message "The model does not exist or you do not have access to it". The app never showed this because `App.tsx` caught the error, logged it to the browser console only, and fell back to the offline generator.

The Netlify log was empty for a different reason: the app does not call the function at all. `App.tsx` imports the generator from `claudeApi.ts`, which calls Groq directly from the browser using `VITE_GROQ_API_KEY`. The function and its client `aiService.ts` are deployed but unused.

### Changes
**`netlify/functions/generate-itinerary.js`**
- `console.error` on every failure path: non-OK HTTP responses now log status, status text, and the first 2,000 characters of Groq's body; thrown errors log name, message, and cause; timeouts log the budget. Client-facing messages are unchanged.
- Model switched to `openai/gpt-oss-120b`, the strongest model the account's key can access.
- `response_format: { type: "json_object" }` turns on Groq's JSON mode, which guarantees parseable output.
- `reasoning_effort: "low"` and `max_tokens` raised from 4,000 to 8,000, because the new model spends reasoning tokens inside the completion budget.
- `temperature` lowered from 0.7 to 0.4 for closer schema adherence.
- Prompt rules 3, 8, and 9 added: at least four items per day, exactly N days numbered 1..N, and `category` limited to the four supported values.
- `normalizeCategory()` maps synonyms onto `transport`, `activity`, `meal`, `accommodation` and defaults anything else to `activity`. The validator now accepts any non-empty category string instead of rejecting unknown ones, because the UI looks up icon and colour by category with no fallback and would crash on an unexpected value.
- `detail` may be an empty string; the UI already renders it conditionally.
- The handler rejects a response whose day count differs from the request, with a clear message.

**`src/app/components/rl/claudeApi.ts`** (the browser path actually in use)
- Same model, JSON mode, reasoning effort, temperature, and prompt rules.
- Same `normalizeCategory()` applied to every item.
- Throws if the returned day count differs from the request, so the fallback path takes over rather than showing a short trip.

### Verification
Three real trips of 7, 10, and 12 days were run end to end through the function against Groq and all passed validation. Type check and production build pass.

### Operational notes
- The Groq account is on the free on-demand tier, limited to 8,000 tokens per minute. One itinerary costs 5,000 to 7,000 tokens, so generating twice inside a minute returns a 429 and the app falls back to the offline itinerary. Space demo generations about a minute apart or upgrade the tier.
- **The Groq key is compiled into the public browser bundle.** Anyone can read it from the site's source and spend the quota. Not fixed in this patch. The fix is to import `generateItineraryWithAI` from `aiService.ts` instead of `claudeApi.ts` in `App.tsx`, add `GROQ_API_KEY` (no `VITE_` prefix) to Netlify's environment variables, then rotate the key in GroqCloud. The function is tested and ready.

## 2. Optional travel month and monsoon warning

### Design rule
The month is never sent to the AI, never enters the prompt, and never touches the serverless functions. It is collected in the form, attached to the finished itinerary client-side, and read after generation to decide whether to show a banner. Trips with no month are unchanged everywhere.

### Changes
**New files**
- `src/app/lib/seasonData.ts` — pure data, no imports. Four regions (South & West, East & North, Hill Country, Cultural Triangle) with avoid, caution, and best months plus opposite-coast alternatives, and a lower-cased city-to-region map covering every name the picker, the map, and older saved trips can produce. Yala, Kalpitiya, and Minneriya were added to South & West, South & West, and Cultural Triangle respectively.
- `src/app/lib/season.ts` — `checkSeason(cities, month)` returns `{ city, region, severity, message, alternative }[]`. Case-insensitive, trims whitespace, de-duplicates, returns `[]` for a null or invalid month, unknown cities, or anything in season.
- `src/app/lib/season.test.ts` — ten tests on Node's built-in runner. Run with `npm test`. No packages added.
- `src/app/components/rl/SeasonBanner.tsx` and `src/styles/season-banner.css` — informational banner in the existing `wr-*` design language, amber for caution, red-edged for avoid, wrapped in try/catch and rendering nothing on error.

**Touched files**
- `types.ts` — one optional field, `travelMonth?: number`, on `GeneratedItinerary`.
- `PlannerScreen.tsx` — "When are you travelling? (optional)" select on the Length step, blank default, no validation.
- `HomeScreen.tsx` — same select on the quick form beside Duration.
- `App.tsx` — `handleGenerate` takes the month as a second argument, separate from `TripInputs`, and attaches it to the itinerary before saving.
- `ItineraryScreen.tsx` — one line rendering `SeasonBanner` under the hero.
- `package.json` — `"test": "node --test \"src/**/*.test.ts\""`.

Persistence needs no schema change: the whole itinerary is stored as JSON in localStorage and in the Supabase `trips.itinerary_json` column.

### City reconciliation
Twelve of the 27 cities in the original region spec match the picker exactly. Fifteen are never selectable but are kept in the data for hand-typed or map-added cities. Verified in the browser: July plus Mirissa produced the avoid banner and the saved trip carried `travelMonth: 7`.

## 3. Map redesign and basemap replacement

### Pins
`src/app/components/rl/mapPins.ts` and `src/styles/map-pins.css` replace the plain coloured dots on all five maps (Explore, itinerary route map, day activity map, Hotels, Routes mini maps).

- Cities are teardrop pins with a category icon: waves for coast, mountain for highlands, temple for heritage, paw for wildlife, building for cities. Colours unchanged from `MARKER_COLORS`.
- Selected pins get a gold ring and a pulsing halo; all pins scale on hover. Reduced-motion users get a static halo.
- Route map: first stop shows a landing plane, last stop a flag, and every stop has a permanent name label. The active stop's label inverts to navy.
- Explore: name labels appear from zoom level 8.
- Day map: numbered stops in the serif brand font, coloured by item category; tonight's stay is a gold teardrop with a bed icon.
- Hotels: rounded-square pins tinted by tier, gold when selected. Discovered places stay as small dots with the same states.
- Route lines get a soft navy underlay for depth; the dashed placeholder animates while the road route loads.
- Icon paths are from lucide (ISC), inlined as SVG strings.

`leafletSetup.ts` is kept for its side effects (Leaflet CSS and default icon fix) and is imported by `mapPins.ts`.

### Basemap
**CARTO's basemaps now render a diagonal "API KEY REQUIRED" watermark on every tile.** This was already visible on the itinerary and hotel maps in production before this patch; it was confirmed by downloading tiles directly, including with the production domain as referer. All maps now share `TILE_LAYER` in `mapConfig.ts`, pointing at Esri World Topo, which needs no key and is free with the attribution shown in the map corner. The Explore map previously used raw OpenStreetMap tiles; it now matches the others.

## 4. Route resolution reaches the AI

### Bug
The planner showed a resolved route (canonical geographic order, capped at six cities and one city per 1.5 days, over-long picks dropped) but both forms sent the raw tap order to the AI. Cities marked "won't fit" were still sent. The route map then drew whatever `cities` array the model returned.

### Changes
- `App.tsx` — `handleGenerate` calls `resolveCities` once, sends the resolved list to the AI, and overwrites the itinerary's `cities` with the same list so the route map and day tabs always match the form.
- `cityPlan.ts` — a matched city now takes its canonical spelling ("kandy" becomes "Kandy") so coordinate and category lookups never miss.

Verified in the browser: tapping Galle, Sigiriya, Negombo in that order produced the route Negombo → Sigiriya → Galle through the AI path.

## Known issues and follow-ups, not in this patch

1. Groq key exposed in the browser bundle (see section 1). Highest priority.
2. Netlify function invocations were at 50% of the free tier on 10 Sep. The only real consumer is the `/api/foursquare` proxy used by the day map and Explore's nearby-place search. All 4,840 Supabase places already have coordinates, so a Supabase-first lookup in `foursquareGeocoder.ts` would remove most calls. The localStorage geocode cache also clears itself entirely when storage is full.
3. Six map-only cities (Jaffna, Kalpitiya, Yala, Minneriya, Unawatuna, Anuradhapura) are not in `CANONICAL_CITY_ORDER` and have no rows in Supabase.
4. Spare days are given to the first and last stop, usually Negombo; a per-city weighting would be better. A relaxed/fast pace option would let users choose one city per day.
5. Supabase `places.style` is empty on every row, so style-filtered hotel queries return nothing and fall back to the hardcoded list. Temple counts (239 in Colombo) look mis-tagged.
6. Pre-existing React warning from `TripsDrawer` about a non-boolean `inert` attribute.
7. Explore legend still shows plain dots rather than the new pin shapes.
